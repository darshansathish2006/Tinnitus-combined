# Deploying EchoSense AI to Render

One web service serves the REST API and the single-page app together. They share
an origin, which is what keeps the deployment simple: there is no CORS
allow-list to maintain, no second service URL to configure, and no API address
baked into the JavaScript bundle.

```
                 ┌─────────────────────────────────────────┐
 browser ──TLS──►│ Render edge                             │
                 │   └─► gunicorn ─► Django                │
                 │         ├─ /api/*  → REST API           │
                 │         ├─ /assets/*, /static/* →       │
                 │         │     WhiteNoise                │
                 │         └─ everything else →            │
                 │               SPA shell (index.html)    │
                 └─────────────────────────────────────────┘
```

## Deploy

1. Push the repository to GitHub.
2. In the Render dashboard: **New → Blueprint**, select the repository.
3. Render reads [`render.yaml`](../render.yaml) and creates the service. The only
   prompt is the optional `ECHOSENSE_ANTHROPIC_API_KEY`; leave it blank and the
   assistant runs on its rules engine.
4. First build takes roughly 8–12 minutes — most of it installing SciPy and
   scikit-learn, bundling the 79 MB intro video, and fitting the ensemble.

The service is live at `https://<name>.onrender.com`. Sign in with the demo
accounts listed at `/api/auth/demo-accounts`.

## What the build does

[`build.sh`](../build.sh) produces everything the running service needs that the
repository does not carry, because all of it is generated output:

| Step | Why it is not committed |
| --- | --- |
| `npm ci && npm run build` | `frontend/dist/` is a build artifact |
| `collectstatic` | `backend/staticfiles/` is a copy of installed packages' assets |
| `migrate` | schema changes must be applied, not assumed |
| `train_models` | `backend/artifacts/` is gitignored; the ensemble is fitted per build |
| `seed_demo` | only when the database is empty — see below |

Run it locally to reproduce a deployment exactly:

```bash
bash ./build.sh
```

## Configuration

Everything is environment-driven; none of it needs a code change.

| Variable | Default | Notes |
| --- | --- | --- |
| `ECHOSENSE_SECRET_KEY` | — | **Required in production.** Generated by the blueprint. Signs JWTs, so the app refuses to start on the development key when `DEBUG` is off. |
| `ECHOSENSE_DEBUG` | `0` on Render, `1` locally | The default is chosen from Render's `RENDER` variable, so a forgotten variable cannot ship a debug build. |
| `DATABASE_URL` / `ECHOSENSE_DATABASE_URL` | unset → SQLite | Any `postgres://` URL. `?sslmode=` is honoured. |
| `ECHOSENSE_ALLOWED_HOSTS` | `*` | Render's own hostname is appended automatically. |
| `ECHOSENSE_CORS_ORIGINS` | empty | Only needed if the frontend is hosted separately. |
| `ECHOSENSE_SSL_REDIRECT` | on when `DEBUG` is off | Set `0` to exercise production settings locally over plain HTTP. |
| `ECHOSENSE_ANTHROPIC_API_KEY` | unset | Without it the assistant uses its rules engine. |
| `ECHOSENSE_SEED` | `auto` | `auto` seeds only an empty database; `always` reseeds every build; `never` skips. |
| `ECHOSENSE_TRAIN_N` | `6000` | Cohort size for training. Lower it to shorten builds. |
| `ECHOSENSE_MEET_LINK` | a standing room | The teleconsultation room. |

The Python version comes from [`.python-version`](../.python-version). Render
does **not** read `runtime.txt` — that file was removed because it never had any
effect.

## Data persistence — read this before demoing

As shipped, the service runs on the SQLite file committed to the repository.
That is free and needs no infrastructure, and every restart returns the demo
cohort to a known-good state. The cost is that **Render's disk is ephemeral**:
anything a user creates is lost when the instance restarts, and on the free plan
the instance also sleeps after 15 minutes of inactivity, so the first request
after a pause takes ~30 seconds to wake it.

For a demo where nothing needs to survive, that is often the right trade. For
anything else, uncomment the `databases:` block and the `DATABASE_URL` entry at
the bottom of `render.yaml`. `settings.py` reads `DATABASE_URL` with no code
change, and `build.sh` seeds the demo cohort the first time it finds the
database empty. Note that Render's free Postgres instances are deleted after 30
days.

## Notes on the free plan

- **512 MB RAM.** gunicorn runs a single worker with four threads. NumPy,
  pandas, scikit-learn and the loaded model bundle account for most of that
  budget once; a second worker would not fit, and an out-of-memory restart loop
  is a worse failure than queueing. If you move to a paid instance, raise
  `--workers` before `--threads`.
- **The 79 MB intro video** is bundled as a Vite asset, so it is served from the
  instance. It dominates build time and the first-load experience. Moving it to
  object storage or a CDN is the single biggest improvement available if the
  onboarding video feels slow.
- **Health checks** hit `/api/health`, which is exempt from the HTTPS redirect —
  the platform reaches the container directly, without the `X-Forwarded-Proto`
  header, so an unexempted check would be answered with a 301 and the service
  would never be marked healthy.

## Verifying a deployment

```bash
curl -s https://<name>.onrender.com/api/health | python -m json.tool
```

`models.available` should be `true`. If it is `false`, the `train_models` step
did not run or did not finish — check the build log.
